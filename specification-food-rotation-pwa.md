# Спецификация веб-приложения для ротации продуктов

## 1. Назначение документа

Этот документ — техническое и функциональное задание для Codex на разработку первой рабочей версии персонального мобильного веб-приложения.

Приложение предназначено для одного пользователя. Оно помогает помнить, какие отслеживаемые продукты недавно были в рационе, соблюдать заданные интервалы между повторениями и выбирать продукты на следующую неделю.

Рабочее название в интерфейсе можно временно указать как **«Ротация»**. Название должно храниться отдельно и легко заменяться позднее без изменения логики приложения.

## 2. Главная пользовательская задача

Пользователь добавляет отдельный продукт, задаёт ему частоту ротации и указывает точную дату или период употребления. Приложение:

1. сохраняет историю;
2. считает следующую допустимую дату от последнего дня последнего периода;
3. показывает, сколько осталось до этой даты;
4. выводит продукты, которые уже можно вернуть в рацион или можно будет вернуть в ближайшие семь дней;
5. нейтрально предупреждает о повторе раньше установленного интервала;
6. показывает календарную историю и статистику разнообразия.

Приложение является инструментом памяти, а не медицинским сервисом. Оно не даёт медицинских рекомендаций, не оценивает продукты как полезные или вредные и не запрещает пользователю добавлять записи.

## 3. Основные принципы продукта

- Отслеживаются только продукты, которые пользователь сам добавил.
- Каждый продукт — независимая позиция. Например, говядина, свинина, минтай, треска и креветки не объединяются автоматически.
- Группы нужны только для организации списка. Они не влияют на расчёты.
- Приложение начинает работу с пустой базой. Предзаполненной библиотеки продуктов нет.
- Фиксируется период присутствия продукта в рационе, а не каждая порция и не количество съеденного.
- Один продукт может иметь несколько периодов в истории.
- Решение о повторном употреблении всегда остаётся за пользователем.
- Формулировки и статусы должны быть нейтральными: «можно снова», «в ближайшие 7 дней», «позже», «повтор раньше интервала».
- Не использовать формулировки «нельзя», «запрещено», «плохой продукт», «нарушение диеты».

## 4. Объём первой версии (MVP)

В MVP входят:

- установка на главный экран Android как PWA;
- полноценная работа без интернета после первого открытия;
- локальное хранение данных без регистрации и сервера;
- резервное копирование и восстановление из файла;
- пользовательские продукты и группы;
- три шаблона интервалов;
- внесение однодневных и многодневных периодов;
- автоматический расчёт следующей даты;
- экран доступности продуктов;
- календарная история;
- карточка продукта с полной историей;
- редактирование и удаление ошибочных записей;
- архив продуктов;
- предупреждение о раннем повторе;
- статистика по месяцам.

В MVP не входят:

- регистрация и аккаунты;
- облачная синхронизация между устройствами;
- уведомления;
- рецепты, блюда и меню;
- калории, БЖУ, нутриенты и вес порций;
- учёт запасов и покупок;
- штрихкоды;
- автоматическая классификация продуктов;
- медицинские рекомендации;
- готовые рационы и сочетания продуктов;
- серверная база данных;
- полноценная визуальная дизайн-система.

## 5. Платформа и техническая реализация

### 5.1. Целевая платформа

- Основное устройство: Android-смартфон.
- Формат: mobile-first PWA.
- Язык интерфейса: русский.
- Часовой пояс: локальный часовой пояс устройства.
- Даты хранятся как локальные календарные даты в формате `YYYY-MM-DD`, без времени и без преобразования через UTC.

### 5.2. Рекомендуемый стек

Codex может выбрать эквивалентный современный стек, но предпочтительны:

- React + TypeScript + Vite;
- IndexedDB для данных, желательно через Dexie;
- service worker и web app manifest для PWA;
- библиотека календарных операций с поддержкой календарных месяцев, например date-fns;
- unit-тесты для расчёта дат и статистики;
- адаптивная вёрстка без зависимости от внешних CDN.

Локальное хранилище `localStorage` нельзя использовать как основное хранилище истории. Основные данные должны находиться в IndexedDB. `localStorage` допустим только для малозначимых настроек интерфейса.

### 5.3. Требования PWA

- Приложение должно иметь manifest, иконки и корректный `display: standalone`.
- После установки оно должно запускаться с главного экрана без обычной панели браузера.
- После первого успешного открытия основной интерфейс и данные должны быть доступны без интернета.
- Все необходимые шрифты, иконки и ресурсы должны поставляться вместе с приложением или иметь безопасный локальный fallback.
- Обновление версии не должно удалять пользовательские данные.

## 6. Модель данных

Идентификаторы рекомендуется хранить как UUID.

### 6.1. Group

```ts
type Group = {
  id: string;
  name: string;
  sortOrder: number;
  createdAt: string;
  updatedAt: string;
};
```

Требования:

- пользователь может создавать, переименовывать и менять порядок групп;
- системная группа «Без группы» существует всегда и не удаляется;
- при удалении пользовательской группы приложение предлагает перенести её продукты в другую группу либо в «Без группы»;
- удаление группы не должно удалять продукты или их историю.

### 6.2. Product

```ts
type RotationRule = "weekly" | "biweekly" | "monthly";

type Product = {
  id: string;
  name: string;
  groupId: string;
  rotationRule: RotationRule;
  isArchived: boolean;
  createdAt: string;
  updatedAt: string;
};
```

Требования:

- название обязательно;
- перед сравнением названий удалить пробелы по краям и привести повторяющиеся пробелы к одному;
- дубликаты проверять без учёта регистра;
- если продукт с таким названием существует, предложить открыть его и добавить новый период;
- архивный продукт не показывается на главном экране, но его история сохраняется;
- архивный продукт можно восстановить;
- изменение правила немедленно пересчитывает следующую доступную дату на основе последнего периода;
- изменение правила не переписывает исторические даты.

### 6.3. ConsumptionPeriod

```ts
type ConsumptionPeriod = {
  id: string;
  productId: string;
  startDate: string; // YYYY-MM-DD
  endDate: string;   // YYYY-MM-DD
  createdAt: string;
  updatedAt: string;
};
```

Требования:

- для однодневного употребления `startDate` равен `endDate`;
- `endDate` не может быть раньше `startDate`;
- даты будущего в MVP не допускаются, потому что приложение фиксирует факт употребления, а не план;
- ошибочный период можно отредактировать или удалить с подтверждением;
- после редактирования или удаления все статусы и статистика пересчитываются;
- несколько периодов одного продукта хранятся отдельно;
- при выводе актуального статуса используется период с самым поздним `endDate`;
- при одинаковом `endDate` более поздним считается период с более поздним `startDate`, затем с более поздним `createdAt`.

### 6.4. AppSettings

```ts
type AppSettings = {
  schemaVersion: number;
  locale: "ru";
  onboardingCompleted: boolean;
};
```

## 7. Правила расчёта дат

### 7.1. Базовая дата

Следующая доступная дата всегда рассчитывается от `endDate` последнего периода.

Пример:

- продукт употреблялся 17–19 сентября;
- последняя дата употребления — 19 сентября;
- расчёт начинается от 19 сентября.

### 7.2. Шаблоны интервалов

| Правило | Расчёт |
| --- | --- |
| Раз в неделю | `endDate + 7 календарных дней` |
| Раз в две недели | `endDate + 14 календарных дней` |
| Раз в месяц | тот же номер следующего календарного месяца |

Для правила «раз в месяц» использовать календарный месяц, а не 30 дней.

Примеры:

- 19 сентября → 19 октября;
- 7 сентября → 7 октября;
- 31 января → последний существующий день февраля;
- 29 февраля високосного года → 29 марта;
- 31 марта → 30 апреля.

Доступная дата включается в разрешённое окно: если следующая дата — 19 октября, то 19 октября продукт уже находится в разделе «Можно сейчас».

### 7.3. Статусы относительно сегодняшней даты

Пусть `availableDate` — следующая доступная дата, а `today` — сегодняшняя локальная дата.

- **Можно сейчас:** `availableDate <= today`.
- **В ближайшие 7 дней:** `today < availableDate <= today + 7 дней`.
- **Позже:** `availableDate > today + 7 дней`.
- Продукт без единого периода считается доступным сейчас, но помечается как «Ещё не отмечался».

Количество оставшихся дней рассчитывается календарными днями, без времени суток.

Примеры:

- дата наступила сегодня → «Можно с сегодня»;
- дата наступила раньше → «Можно снова» и дополнительная подпись «доступно с 8 октября»;
- осталось 1 день → «через 1 день»;
- осталось 2–4 дня → корректное склонение «через 2 дня»;
- осталось 5–20 дней → «через 5 дней».

### 7.4. Фактическое повторение после доступной даты

Если продукт можно было повторить 8 октября, но пользователь внёс новый период только 15 октября, новый отсчёт ведётся от фактического `endDate` нового периода.

Пример:

- доступно с 8 октября;
- новый период: 15 октября;
- следующее окно при месячном правиле: 15 ноября.

Неиспользованное окно не запускает новый цикл автоматически.

## 8. Ранний повтор

Ранним повтором считается новый период, у которого `startDate` раньше доступной даты, рассчитанной по предшествующему периоду этого продукта.

Если пользователь добавляет такой период, показать нейтральное модальное окно:

> **Этот продукт уже был недавно**  
> Предыдущий период закончился 7 сентября.  
> По выбранному интервалу следующее окно начинается 7 октября.

Действия:

1. **Изменить предыдущий период** — открыть форму последнего периода и предложить изменить его конечную дату;
2. **Всё равно добавить** — сохранить новый отдельный период;
3. **Отмена** — ничего не сохранять.

Приложение никогда не блокирует запись окончательно.

Если пользователь выбирает «Изменить предыдущий период»:

- исходная дата начала сохраняется;
- пользователь сам выбирает новую дату окончания;
- после сохранения статус пересчитывается от новой даты окончания.

Если между употреблениями был важный для пользователя перерыв, он может выбрать «Всё равно добавить» и сохранить два отдельных периода.

Признак раннего повтора лучше вычислять по актуальной истории, а не хранить как неизменяемый флаг. Тогда после исправления или удаления записей статистика останется корректной.

## 9. Навигация

В нижней навигации четыре вкладки:

1. **Можно снова** — стартовый экран;
2. **Календарь**;
3. **Продукты**;
4. **Статистика**.

На основных экранах доступна заметная кнопка **«Добавить»**. Допустим плавающий FAB с подписью или понятной иконкой, но одна иконка без доступного названия недопустима.

## 10. Экран «Можно снова»

Это первый экран после запуска.

### 10.1. Содержание

Три последовательно расположенных раздела:

1. **Можно сейчас**;
2. **В ближайшие 7 дней**;
3. **Позже**.

Внутри каждого раздела продукты разбиваются по пользовательским группам.

Карточка или строка продукта содержит:

- название;
- название группы, если контекст группы визуально неочевиден;
- последнюю дату или период;
- правило ротации;
- доступную дату либо количество оставшихся дней;
- действие для быстрого внесения нового периода.

Для продукта без истории показывать «Ещё не отмечался».

### 10.2. Сортировка

- группы — по пользовательскому `sortOrder`, затем по названию;
- «Можно сейчас» — сначала продукты без истории, затем по самой ранней доступной дате;
- «В ближайшие 7 дней» и «Позже» — по возрастанию доступной даты;
- при одинаковой дате — по названию продукта.

### 10.3. Пустые состояния

Если база полностью пуста:

> Здесь появятся продукты, частоту которых вы хотите отслеживать.  
> Добавьте первый продукт и укажите, когда он был в рационе.

Кнопка: **«Добавить первый продукт»**.

Пустые разделы не должны занимать много места. Допустимо показывать короткую подпись либо скрывать раздел, если хотя бы один другой раздел содержит продукты.

## 11. Добавление продукта и периода

### 11.1. Общий сценарий

После нажатия «Добавить» пользователь видит поле поиска/названия.

- По мере ввода показываются совпадения среди активных и архивных продуктов.
- При выборе существующего активного продукта открывается форма нового периода.
- При выборе архивного продукта предлагается восстановить его и добавить период.
- Если совпадений нет, доступно действие **«Создать продукт “…”»**.

### 11.2. Создание нового продукта

Поля:

1. название продукта — обязательно;
2. группа — обязательно, по умолчанию «Без группы»;
3. возможность создать новую группу прямо из формы;
4. интервал — обязательно:
   - раз в неделю;
   - раз в две недели;
   - раз в месяц;
5. период употребления:
   - дата начала;
   - дата окончания;
   - по умолчанию обе даты равны сегодняшнему дню.

Основная кнопка: **«Сохранить»**.

После сохранения показать короткое подтверждение, например:

> Говядина добавлена. Можно снова с 19 октября.

### 11.3. Новый период существующего продукта

Поля:

- название продукта — только для чтения;
- текущая группа и правило — краткой подписью;
- дата начала;
- дата окончания;
- ссылка **«Изменить правило продукта»**.

Перед сохранением проверить ранний повтор.

## 12. Экран «Календарь»

### 12.1. Общий вид

- обычная месячная сетка;
- переключение на предыдущий/следующий месяц;
- кнопка «Сегодня»;
- понедельник — первый день недели;
- русские названия месяцев и дней недели.

### 12.2. Отображение записей

- Однодневный период отмечается на соответствующем дне.
- Многодневный период визуально продолжается через все дни от `startDate` до `endDate` включительно.
- На маленьком экране не пытаться разместить все длинные названия внутри ячейки.
- Допустимы короткие цветовые маркеры/полосы и счётчик дополнительных записей.
- Под календарём всегда находится список продуктов выбранного дня с полными названиями.
- По умолчанию выбран сегодняшний день, а при просмотре другого месяца — первый день месяца с записями либо первое число.

Нажатие на запись открывает карточку продукта или нижний лист с действиями:

- открыть историю продукта;
- изменить период;
- удалить период.

Удаление периода требует подтверждения:

> Удалить период 17–19 сентября? История и следующая доступная дата будут пересчитаны.

## 13. Экран «Продукты»

### 13.1. Список

- поиск по названию;
- группировка по группам;
- фильтры «Активные» и «Архив»;
- сортировка по имени или по дате последнего употребления;
- управление группами;
- кнопка создания продукта без обязательного периода допустима.

Если продукт создаётся без периода, он попадает в «Можно сейчас» со статусом «Ещё не отмечался».

### 13.2. Карточка продукта

Показывать:

- название;
- группу;
- правило ротации;
- последний период;
- следующую доступную дату;
- текущий статус;
- полную историю периодов от новых к старым;
- нейтральную отметку возле периодов, начавшихся раньше интервала.

Действия:

- добавить новый период;
- изменить название;
- изменить группу;
- изменить правило;
- отредактировать период;
- удалить ошибочный период;
- переместить продукт в архив;
- восстановить из архива.

При архивации объяснить:

> Продукт исчезнет из активных списков, но его история сохранится.

## 14. Экран «Статистика»

### 14.1. Выбор периода

- по умолчанию открыт текущий месяц;
- можно переключаться между месяцами;
- статистика строится только по отслеживаемым продуктам и их периодам.

### 14.2. Метрики

#### Разнообразие месяца

Количество уникальных продуктов, у которых хотя бы один день периода пересекается с выбранным календарным месяцем.

Один продукт считается один раз, даже если в месяце у него несколько периодов.

Пример:

> В сентябре в рационе было 18 разных отслеживаемых продуктов.

#### Сравнение с предыдущим месяцем

Сравнить количество уникальных продуктов с предыдущим календарным месяцем.

Формулировки:

- больше: «В этом месяце разнообразие увеличилось: 18 продуктов против 14 в августе»;
- меньше: «В этом месяце разнообразие уменьшилось: 12 продуктов против 17 в августе»;
- одинаково: «Разнообразие осталось на прежнем уровне: по 15 продуктов»;
- недостаточно данных: «Сравнение появится после данных за предыдущий месяц».

Не использовать оценочные слова «хорошо», «плохо», «скудно».

#### Новые продукты

Продукт считается новым в выбранном месяце, если его самый первый период за всю историю начинается в этом месяце.

Пример:

> Впервые отмечены: козье молоко, кальмар и сыр бри.

Создание карточки продукта без периода не делает продукт «новым» для статистики.

#### Ранние повторы

Показать:

- количество уникальных продуктов, у которых в выбранном месяце начался хотя бы один ранний повтор;
- список этих продуктов;
- по нажатию — конкретные периоды и ожидаемые даты.

Если один продукт повторился рано дважды, в главном числе он считается один раз, но в деталях отображаются оба случая.

#### Давно не было в рационе

Показать до пяти активных продуктов с наиболее давней последней датой употребления. Продукты без истории выводить отдельно как «Ещё не отмечались».

Если данных мало, скрывать карточку или показывать спокойное пустое состояние.

### 14.3. Периоды на границе месяца

Если период длится с 30 сентября по 2 октября, продукт учитывается в разнообразии и сентября, и октября. При этом новым продуктом он считается только в сентябре, потому что первый период начался в сентябре.

## 15. Резервная копия и восстановление

В настройках или в меню экрана «Продукты» добавить раздел «Данные».

### 15.1. Экспорт

- кнопка **«Сохранить резервную копию»**;
- выгрузка одного JSON-файла;
- имя файла, например `rotation-backup-2026-09-22.json`;
- файл содержит версию схемы, дату экспорта, настройки, группы, продукты и периоды;
- не включать служебный кэш PWA.

### 15.2. Импорт

- кнопка **«Восстановить из файла»**;
- проверить формат, версию схемы и обязательные поля;
- показать предварительный итог: число групп, продуктов и периодов;
- в MVP восстановление полностью заменяет текущие данные;
- перед заменой требуется явное подтверждение;
- при ошибке исходные данные должны остаться без изменений;
- после успешного импорта пересчитать статусы и статистику.

Текст предупреждения:

> Восстановление заменит текущие данные содержимым резервной копии. Перед продолжением можно сохранить текущую копию.

## 16. Минимальные требования к интерфейсу

Полная дизайн-система будет разработана отдельно. На первом этапе необходимо:

- mobile-first компоновка;
- комфортная работа одной рукой;
- зоны нажатия не менее 44×44 CSS-пикселей;
- читаемый текст без горизонтальной прокрутки;
- поддержка длинных названий;
- понятные подписи у иконок и кнопок;
- видимый фокус для клавиатурной навигации;
- достаточный контраст;
- корректная работа при системном увеличении текста;
- уважение настройки `prefers-reduced-motion`;
- не использовать красный как основной цвет статуса раннего повтора;
- не строить систему на противопоставлении «зелёное — хорошо, красное — плохо»;
- предусмотреть семантические дизайн-токены, чтобы позднее заменить цвета, шрифты и скругления без переписывания компонентов.

До создания отдельной дизайн-системы использовать спокойную нейтральную палитру и минимальное количество декоративных элементов.

## 17. Ошибки и защита данных

- Все формы должны валидироваться до записи в базу.
- Ошибка интерфейса не должна очищать локальные данные.
- Операции импорта должны быть атомарными: либо импортируются все валидные данные, либо не меняется ничего.
- При недоступности IndexedDB показать понятное сообщение и не создавать ложное впечатление, что данные сохранены.
- После любой успешной записи интерфейс должен сразу отображать пересчитанный статус.
- Не выполнять сетевые запросы для основной функциональности.
- Не подключать аналитику, рекламу или сторонние трекеры.
- Не отправлять пользовательские данные во внешние сервисы.

## 18. Основные пользовательские сценарии

### Сценарий A. Первый запуск

1. Пользователь открывает приложение.
2. Видит пустой экран «Можно снова».
3. Нажимает «Добавить первый продукт».
4. Вводит «Говядина».
5. Выбирает или создаёт группу «Мясо и птица».
6. Выбирает «Раз в месяц».
7. Указывает период 17–19 сентября.
8. Сохраняет.
9. Приложение показывает: «Можно снова с 19 октября».

### Сценарий B. Воскресное планирование

1. Пользователь открывает приложение.
2. Сразу видит раздел «Можно сейчас».
3. Просматривает доступные продукты по группам.
4. Ниже видит продукты, которые станут доступны в ближайшие семь дней.
5. Самостоятельно выбирает продукты для покупок и рациона. Приложение не составляет меню.

### Сценарий C. Продолжение ранее открытого продукта

1. Последний период молока указан как 1–3 сентября.
2. 6 сентября пользователь снова добавляет молоко.
3. Приложение сообщает, что продукт уже был недавно.
4. Пользователь выбирает «Изменить предыдущий период».
5. Меняет окончание периода на 6 сентября.
6. Следующая доступная дата пересчитывается от 6 сентября.

### Сценарий D. Отдельный ранний повтор

1. Последний период продукта закончился 7 сентября.
2. Следующая доступная дата — 7 октября.
3. Пользователь добавляет новый период 20–21 сентября.
4. Видит предупреждение.
5. Выбирает «Всё равно добавить».
6. Период сохраняется отдельно.
7. Следующая доступная дата рассчитывается от 21 сентября.
8. В статистике сентября появляется ранний повтор.

### Сценарий E. Фактическое употребление позже окна

1. Продукт доступен с 8 октября.
2. Пользователь употребляет его только 15 октября.
3. Добавляет период 15 октября.
4. При месячном правиле приложение показывает следующую дату 15 ноября.

### Сценарий F. Исправление ошибки

1. Пользователь открывает запись в календаре.
2. Исправляет дату или удаляет период.
3. Приложение пересчитывает карточку продукта, главный экран, календарь и статистику.

## 19. Приёмочные критерии

Приложение считается готовым к первой проверке, если выполнены все условия:

1. Устанавливается на главный экран Android и открывается как standalone PWA.
2. После первого открытия работает в авиарежиме.
3. Данные сохраняются после закрытия и повторного открытия.
4. Можно начать с пустой базы и создать собственную группу.
5. Можно создать продукт и выбрать один из трёх интервалов.
6. Можно указать один день или период.
7. Следующая дата считается от последнего дня периода.
8. «Раз в месяц» означает календарный месяц, включая корректную обработку 29–31 числа.
9. Главный экран корректно делит продукты на три раздела относительно локальной сегодняшней даты.
10. Новый фактический период запускает новый отсчёт от своей конечной даты.
11. Ранний повтор вызывает нейтральное предупреждение с тремя действиями.
12. Можно расширить предыдущий период либо сохранить новый отдельно.
13. Календарь показывает однодневные и многодневные записи.
14. Можно редактировать и удалять ошибочные периоды.
15. Можно менять название, группу и правило продукта.
16. Можно архивировать и восстанавливать продукт без потери истории.
17. Статистика правильно считает уникальные продукты, сравнение месяцев, новые продукты и ранние повторы.
18. Период на границе месяцев учитывается в разнообразии обоих месяцев.
19. Экспорт создаёт валидную резервную копию.
20. Импорт валидного файла полностью восстанавливает данные, а невалидный файл не повреждает текущую базу.
21. В интерфейсе нет обязательных сетевых функций, рекламы, аналитики и сторонних трекеров.
22. На основных мобильных разрешениях нет горизонтальной прокрутки и недоступных кнопок.

## 20. Обязательные тесты логики

Codex должен добавить автоматические тесты как минимум для следующих случаев:

- недельный интервал: 19 сентября → 26 сентября;
- двухнедельный интервал: 19 сентября → 3 октября;
- месячный интервал: 19 сентября → 19 октября;
- 31 января → 28 февраля или 29 февраля в високосном году;
- 31 марта → 30 апреля;
- период 17–19 сентября → расчёт от 19 сентября;
- доступная дата, совпадающая с сегодняшней, относится к «Можно сейчас»;
- дата через семь дней относится к «В ближайшие 7 дней»;
- дата через восемь дней относится к «Позже»;
- новый период после наступления окна запускает отсчёт от фактической конечной даты;
- ранний повтор определяется по дате начала нового периода;
- удаление последнего периода возвращает статус к предпоследнему периоду;
- изменение правила пересчитывает статус;
- период на границе месяцев учитывается в обоих месяцах;
- один продукт с несколькими периодами считается в разнообразии месяца один раз;
- первый период продукта определяет месяц появления нового продукта;
- импорт повреждённого файла не изменяет текущие данные.

## 21. Порядок реализации

Рекомендуемый порядок:

1. настроить TypeScript-проект, PWA manifest и локальную базу;
2. реализовать модели данных и чистые функции расчёта дат;
3. покрыть расчёты тестами;
4. реализовать создание групп, продуктов и периодов;
5. реализовать экран «Можно снова»;
6. реализовать предупреждение раннего повтора;
7. реализовать карточку продукта и редактирование истории;
8. реализовать календарь;
9. реализовать статистику;
10. реализовать архив, экспорт и импорт;
11. проверить offline-режим и установку PWA на Android;
12. провести мобильное тестирование всех приёмочных сценариев.

## 22. Указание для Codex

Сначала реализовать функционально завершённый MVP в соответствии с этой спецификацией. Не добавлять рецепты, калории, меню, запасы, уведомления, автоматические категории или облачную авторизацию без отдельного запроса.

Если при реализации обнаружится неоднозначность, выбрать самое простое решение, которое:

1. сохраняет пользовательские данные;
2. не блокирует внесение фактической информации;
3. сохраняет нейтральный характер приложения;
4. не расширяет границы MVP.

После сборки предоставить инструкцию:

- как запустить проект локально;
- как собрать production-версию;
- как установить PWA на Android;
- где хранятся данные;
- как создать и восстановить резервную копию;
- как выполнить автоматические тесты.
